# Architecture

## Workspace

| Package                                  | Owns                                                |
| ---------------------------------------- | --------------------------------------------------- |
| `apps/web` (`@meetings/web`)             | TanStack Start app: routes, layouts, features       |
| `packages/backend` (`@meetings/backend`) | Convex schema and functions, typed client API       |
| `packages/ui` (`@meetings/ui`)           | COSS UI components, Kloq calendar, hooks, theme CSS |

Rules:

- Shared versions live in the pnpm catalog (`pnpm-workspace.yaml`). Packages reference them with `catalog:`.
- Lint and format config lives only in the root `vite.config.ts`.
- `#/…` imports are package-local and always include the file extension (`#/lib/utils.ts`).
- Functions are arrow functions assigned to `const`, enforced by the `func-style` lint rule. Vendored COSS files are exempt. Route components are defined above `export const Route` because `const` isn't hoisted.
- First-party code has no comments. Names, types and this file carry the meaning. Vendored COSS files and generated files stay as shipped.
- Kloq (`packages/ui/src/components/kloq`) is the coss calendar, copied from its registry (`https://coss.com/kloq/r/kloq.json`, MIT). It stays as shipped and is excluded from format and lint, so it can be replaced wholesale on update. Import it through `@meetings/ui/kloq`, `@meetings/ui/kloq/rrule`, `@meetings/ui/kloq/timezone` and `@meetings/ui/kloq/rrule-builder`.

## Backend (`packages/backend/convex`)

| Folder      | Contains                                                                                                             | Generated path                  |
| ----------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `api/`      | Public functions only: Zod `args`, then a call into `models/`                                                        | `api.api.<file>.<fn>`           |
| `internal/` | Internal functions only: Convex Auth callbacks, workpool jobs                                                        | `internal.internal.<file>.<fn>` |
| `models/`   | Plain TypeScript business logic that takes `ctx`. All reads and writes live here.                                    | none                            |
| `tables/`   | One Zod schema per table plus `defineTable(zodToConvexFields(...))`, one file per domain. `schema.ts` composes them. | none                            |
| `lib/`      | Building blocks: function middleware, shared Zod validators, workpool instances, email HTML escaping (`html.ts`)     | none                            |

### Data model

[`packages/backend/SCHEMA.md`](packages/backend/SCHEMA.md) has the generated diagram of every table, relationship and index. CI posts it on any PR that changes it.

| Table                 | Belongs to   | Purpose                                                                                                                        |
| --------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `users`               | –            | Identity and profile only. Nothing org-specific.                                                                               |
| `organizations`       | –            | The tenant boundary                                                                                                            |
| `members`             | organization | `orgId` + `userId`. A row means "in this org".                                                                                 |
| `roles`               | organization | Named roles an org defines. `permissions` maps each fixed permission (such as `inviteMembers`, `createMeetings`) to on or off. |
| `memberRoles`         | member       | Assigns roles to a member. A member holds every permission any of their roles grants.                                          |
| `tokens`              | –            | Secret values that expire. Links in old emails stop working once their token expires.                                          |
| `invites`             | organization | Org invite: which role a newcomer gets, who invited them, and the token in the link                                            |
| `joinLinks`           | organization | Shareable invite link: role, use count and limit, the token, revoked time                                                      |
| `auditEvents`         | organization | Who changed membership, roles, invites, links or settings, and when                                                            |
| `meetings`            | organization | Who created it, its title, and `endedAt` once its call emptied and it closed                                                   |
| `meetingTimes`        | meeting      | When it happens: `date` (epoch day), `start` / `end` (`HH:mm`), `timeZone`. Luxon turns these into instants per person.        |
| `meetingMembers`      | meeting      | Who is invited (`pending` / `accepted` / `declined`)                                                                           |
| `meetingGuests`       | meeting      | A guest without an account: their user, who invited them, and the token for their pass                                         |
| `joinRequests`        | meeting      | Someone asking to join an `ask` meeting or a room's waiting room (`waiting` / `denied`); a guest's row holds their pass token  |
| `messages`            | meeting      | The meeting's chat. Each message is written by a meeting member. `pending` while a public room's check is running.             |
| `messageReactions`    | meeting      | One emoji reaction by one meeting member on one message                                                                        |
| `rings`               | meeting      | One person calling another now: caller, callee and `ringing` / `accepted` / `declined` / `missed` / `cancelled`                |
| `strokes`             | meeting      | A drawing on a screen share: presenter, colour and normalized points                                                           |
| `annotationSnapshots` | meeting      | A saved PNG of a screen share with its drawing                                                                                 |
| `schedules`           | user         | Weekly availability, ISO weekdays (1 = Monday)                                                                                 |
| `verifiedSessions`    | –            | Sign-in sessions that passed the passkey step                                                                                  |
| `rooms`               | meeting      | A public room's directory entry: description, how many people are in its call now, and `closedAt`                              |
| `moderationFlags`     | organization | Something the automatic checks acted on in a public room: the removed text or kept frame, Jev's scores, and what was done      |
| `bans`                | organization | Someone banned from the org's public rooms, by user and (for guests) device, with an expiry or until lifted                    |

Rules:

- One table per file in `tables/`, each exporting its Zod schema and table. Field rules are reached through `.shape` (for example `zUser.shape.bio`).
- Tables and public `args` are validated with Zod, via `convex-helpers/server/zod4`. Time values use the Luxon-backed validators in `lib/time.ts`. Convex `v` validators appear only where a library requires them: middleware arguments and the Convex Auth callbacks.
- Convex tables only enforce field types. Model functions call `parseOrThrow(zTable, value)` from `lib/validate.ts` before every `insert`, `patch` or `replace`, so trimming, length and format rules always apply.
- Public queries and mutations have no `returns`. Internal functions declare `returns` only where a library needs it (the Convex Auth `createUser` callbacks).
- List queries paginate with Convex's `paginationOptsValidator`, `.paginate()` on the server, and `usePaginatedQuery` on the client. Single-document reads stay plain.
- Function builders in `lib/functions.ts`:
  - `publicQuery` takes Zod args and needs no sign-in (invite previews).
  - `authedQuery` / `authedMutation` inject `ctx.userId`, or throw `ConvexError("Unauthenticated")`, or `ConvexError("Passkey required")` while the session hasn't passed the passkey step. `orgQuery`, `orgMutation` and the meeting builders (for signed-in callers) check the same.
  - `signedInQuery` / `signedInMutation` inject `ctx.userId` and `ctx.sessionId` without the passkey check. Only the passkey step (`api/passkeys.ts`) uses them.
  - `orgQuery` / `orgMutation` take `orgId` and inject `ctx.userId`, `ctx.member` and `ctx.requirePermission(permission)`. They throw `ConvexError("Not a member")` for anyone outside the org.
  - `zPaginationOpts` is Convex's `paginationOptsValidator` converted to Zod, for the `paginationOpts` arg of list queries.
  - `OrgQueryCtx` / `OrgMutationCtx` are the context types for model functions that run inside them.
- `ctx.run*`, the scheduler and workpools only target `internal.internal.*`.
- Meeting models are split by concern: `models/meetings.ts` schedules, lists and cancels meetings; `models/messages.ts` holds chat and reactions; `models/callSessions.ts` holds the RealtimeKit join details, webhook session lifecycle and recaps; `models/meetingAccess.ts` holds the access checks (`requireMeetingMember`, `requireSessionAccess`, `findSessionByNumber`). `meetingAccess.ts` imports no other model, so the others can all depend on it without a cycle. `models/sessions.ts` is unrelated: it wraps Convex Auth sign-in sessions.
- Environment variables are declared in `convex.config.ts` and read through the typed `env` from `_generated/server`.
- Email goes out through `@sarant/cloudflare-email-component` (`components.cloudflareEmail`) from actions on `emailWorkpool`, which never retries because Cloudflare has no idempotency key. It needs `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` (Email Sending: Edit) and `EMAIL_FROM` on an onboarded domain.
- Roles: every org has the built-in Owner and Admin (all permissions, can't be edited or deleted) and Member (default for invites, can't be renamed or deleted) roles, plus any custom roles. `manageRoles` covers changing members' roles and editing roles; `manageOrganization` covers renaming, domain join, the activity log and seeing when members were last active. Escalation rules live in `models/orgs.ts`: `assertCanGrant` (you can only create, edit, assign or hand out by link a role whose permissions you hold; only owners give the Owner role) and `assertOutranks` (you can't change or remove someone with permissions you lack, or an owner unless you are one). Deleting a role moves its holders to Member. Nobody can remove, demote or leave as the last owner.
- Meetings: Convex owns every meeting, invitee, chat message and recap. Cloudflare RealtimeKit only carries audio and video. The first Join creates the RealtimeKit meeting; each person joins with a preset from `lib/presets.ts` (kind × host or participant), with RealtimeKit's own chat turned off. Joining opens a full-screen call (`?call=true` on `/meetings/$code`) built in `features/meetings/call/`: a lobby with a preview and device pickers, the room, and a left-the-call screen with Rejoin. Every control is our own button. Panels and dialogs that RealtimeKit draws (people, polls, plugins, AI transcript, settings, breakout rooms, Leave confirmation) open by dispatching its `rtkStateUpdate` event (`emitCallUi` in `call/call-ui.ts`); the open panel is `?side=` and chat is the Convex chat. While someone shares a screen, `call/share-stage.tsx` shows it large with a people strip (`?expand=true` hides the strip). Plugins are registered when joining (`whiteboardPlugin`: Cloudflare's hosted whiteboard in an iframe); add more by appending to `defaults.plugins` in `meeting-call.tsx`. RealtimeKit components are themed with `provideRtkDesignSystem`.
- Call controls (`models/calls.ts`): the host, or anyone with `manageMeetings` in the org, can remove a person from a call (`meetingMembers.removedAt`, which blocks joining and chat until they're let back in) and end a call for everyone. Both call RealtimeKit's kick APIs from a scheduled action; kicks use `participant_ids` (the stored `rtkParticipantId`), because `custom_participant_ids` silently matches nobody. Removing someone from the org also removes them from its live calls. Live presence is one `callPeers` row per connected device (`sessionId`, `meetingId`, `memberId`, `peerId`), inserted on the webhook's join event while the session is open and deleted on leave, on `meeting.ended`, and by `forgetDevices` (from `calls.leftOnDevice`, which a device calls itself when it leaves because webhooks can arrive out of order, and from "Switch here"). Queries read these rows through an index, so a join only re-runs the queries that read that session's or that member's peers. `calls.live` lists the org's open sessions for the "Live now" card on Members.
- Meetings end when their call empties (public rooms are the exception, see Public rooms): whenever a leave, `meeting.ended` or `forgetDevices` leaves a meeting with no `callPeers`, `endWhenEmpty` schedules `internal.realtime.endIfEmpty` for two minutes later (`EMPTY_CALL_GRACE_MS`, so a refresh or a quick rejoin doesn't end it). If the call is still empty then, `endEmptyMeeting` sets `meetings.endedAt`, cuts the meeting's time to when it ended (a repeating meeting's rule gets `UNTIL`, so later occurrences disappear from the calendar and busy times) and deactivates the RealtimeKit meeting. This applies to every meeting, scheduled and repeating ones included. An ended meeting can't be joined ("This meeting has ended"); its page and the guest page show when it ended, and Home leaves it out of Upcoming.
- Ringing: the phone button on Members calls `rings.ring`, which starts an instant meeting with the callee invited quietly (`createMeeting` with `quiet`: no inbox item or email), adds a `rings` row and opens the call for the caller. `IncomingCall` in the `_app` layout shows the callee a dialog with a ringtone (`public/ring.wav`) while `rings.incoming` has a ringing row; Answer joins the call, Decline closes it. `internal.rings.expire` turns an unanswered ring into `missed` after 30 s (`RING_MS`) and leaves a missed-call inbox item. The caller sees the ring's state over the call (`call/outgoing-ring.tsx`) and can stop ringing.
- Several devices: one person can be in a call from several devices; they share a RealtimeKit participant (`userId`) and each has its own peer id. In the call, `call/other-devices.tsx` shows a banner when another joined peer has your `userId`; its buttons broadcast an `own-device` message to those peers, which mute themselves, turn their camera off or leave. Before joining, the lobby warns when `me.devicesInCall` is above zero and offers Switch here (`calls.switchHere` kicks your other connections and clears them from presence) or Join on this device too.
- Annotations: while someone shares a screen, everyone can draw on it (`call/annotations.tsx`). Strokes are `strokes` rows keyed by meeting and the presenter's meeting member id, synced by Convex queries, with points normalized to the shared video. The presenter or a host clears them, and they're deleted when the call ends. Saving draws the current frame plus strokes to a PNG in Convex storage (`annotationSnapshots`), shown on the recap. The pen colour is `?draw=`.
- Protected meetings (`meetings.protected`): recording is off, only hosts save snapshots or download the recording, and right-click and drag are disabled on the call stage. Browsers can't block screenshots.
- Chat history: chat is per meeting and kept. The recap shows the messages sent during that session; the in-call chat marks where this call started.
- Chat UI is built from COSS UI's chat package (`@meetings/ui/chat/*`): `ChatConversation`, `ChatMessage` bubbles and the `Composer`, in `features/meetings/meeting-chat.tsx`. Reactions are one `messageReactions` row per person and emoji from a fixed set of six (`REACTION_EMOJIS`); `messages.react` toggles yours, guests included, and `messages.list` returns each message's counts, whether you reacted and up to ten names.
- Meeting access: `meetings.access` is who can join (`invited`, the default; `org`, anyone in the organization; `ask`, the organization walks in and anyone else with the link asks; `link`, anyone with the link, including guests; `public`, a public room, set only by `rooms.create`) and `meetings.inviters` is who can invite (`hosts`, the default, or `everyone` in the meeting). Hosts change both, and Protected, in the Access card. Signed-in people who aren't on the list see the meeting's door (`meetings.door`) and walk in with `meetings.enter` when access allows. `meetings.invite` takes emails: people in the org are added and notified, and anyone else becomes a guest.
- Asking to join (`models/joinRequests.ts`): on `ask` meetings, a signed-in person outside the org asks from the door (`joinRequests.ask`), and a guest asks from `/m/$code` with a name (`guests.enter` opens a request instead of a pass, and returns a secret whose `/guest/$secret` page waits). Each ask notifies the hosts (`joinRequest` in the inbox). Hosts and meeting managers see `JoinRequests` (`features/meetings/join-requests.tsx`) on the meeting page and as a strip in the call, and answer with `joinRequests.admit` (adds the meeting member, and for a guest the `meetingGuests` pass on the waiting token) or `joinRequests.deny` (the person sees it and can ask again). Nobody is a meeting member while waiting, so no meeting data reaches them. Cancelling a meeting deletes its requests and their guest users.
- Guests have no account. A guest is a `users` row with method `guest`, a normal `meetingMembers` row and a `meetingGuests` pass: a random secret whose SHA-256 is in `tokens` (30 days). Invited guests get a personal `/guest/$secret` link by email; on `link` meetings anyone can open `/m/$code`, type a name and get one. Meeting functions guests use (`meetings.get`, `meetings.join`, `messages.*`, `annotations.*`) are built with `meetingQuery`/`meetingMutation`/`meetingAction`, which accept either a session or the `guest` secret; the pass only works for its own meeting because the guest is a member of nothing else. On the client, `GuestPassContext` (`features/meetings/guest-pass.ts`) adds the secret to those calls. Cancelling a meeting deletes its guests. Convex Auth's anonymous method isn't public yet, which is why guests use passes rather than sessions.
- Meetings are addressed by a short `code` (`abc-defg-hij`), never by their table id. URLs, links and the header's "Code or link" box all use it. `internal.internal.realtime.setup` creates the presets and registers the webhook (`/realtime/webhook`, RSA-signed) once per deployment. It needs `REALTIMEKIT_APP_ID` and `REALTIMEKIT_API_TOKEN` (Realtime Admin).
- Recaps: each call is a `meetingSessions` row filled by the RealtimeKit webhook. The summary is stored as text. The transcript is downloaded as JSON into Convex storage (`transcriptId`). Recordings go to your R2 bucket (configured once in the RealtimeKit dashboard) and are addressed by `recordingKey` (`RECORDINGS_PATH` + file name). `meetings.recordingUrl` signs an R2 link with `@convex-dev/r2` when `R2_*` is set, else falls back to Cloudflare's 7-day link.
- Attendance: `meetingSessions.attendance` has one entry per person: first join, last leave and seconds in the call. A stretch starts when their first device joins and ends when their last one leaves, so several devices count once. `callPeers.joinedAt` carries the stretch start; `removePeer` in `models/calls.ts` closes it and is the only way peers are removed during a call.
- Meeting invite emails: scheduling a meeting or inviting org members to one queues `internal.meetingEmails.send` on `emailWorkpool` for each invitee (`queueMeetingEmails` in `models/meetingEmails.ts`), with an `.ics` from `lib/ics.ts` (`METHOD:REQUEST`, UID `<code>@convex-meetings`, times in the meeting's zone). Cancelling a meeting that hasn't ended sends `METHOD:CANCEL` to everyone who hadn't declined, guests included. Replies from the recipient's calendar app go to `EMAIL_FROM` and aren't read back; people reply in the app.
- Inbox: `notifications` rows are written by meeting create (invite), respond (to the host), cancel, and the first summary of a call (recap ready). `inbox.unreadCount` feeds the sidebar badge.
- Invites: the link carries a random secret; `tokens.value` stores only its SHA-256. Links expire after 7 days and work once. Accepting one marks the user verified with the invited address.
- Joining an org: email invites (up to 50 at once, existing members skipped), invite links (`joinLinks`: a role, an expiry of 1, 7 or 30 days, an optional use limit; the secret is shown once and only its hash is kept), and domain join (`organizations.joinDomain`: people with a verified email at that domain see the org on the empty-org screen and on `/orgs/new` and join with a click; setting it needs your own verified email there, and public mail providers are refused).
- Activity: `auditEvents` rows come from the `audit()` helper in `models/audit.ts`, called by every mutation that changes membership, roles, invites, links, domain join or the org name. Org settings shows them to `manageOrganization`.
- Sign-in: Google or GitHub, then a passkey, every time. Only the Google and GitHub methods are set up in `api/auth.ts`; there is no username, password or passkey-only sign-in. `requireSignedIn` in `models/passkeys.ts` refuses any account whose `users.method` isn't `google` or `github` ("Sign in with Google or GitHub"), so older username accounts can't use the app even with a live session. The one exception is development: when a deployment has `DEV_EMAIL_SIGN_IN=true`, the sign-in page also shows an email and password form (`usernamePassword` with the email as the username, `features/auth/dev-email-form.tsx`). It sends no email, the account's `method` is `devEmail`, and it skips the passkey step. `internal/users.ts` refuses to create or sign in such accounts on any deployment without the switch, and `requireSignedIn` refuses existing ones there too, so never set it in production. Backend tests swap the WASM password hash for `tools/password-hash.ts`. Every session must also pass a passkey step before the builders above let it through: a `verifiedSessions` row for its session id (the access token's `sub`). Convex Auth 2.0 has no step-up primitive, and its passkey management needs a username, so `models/passkeys.ts` drives the passkey component directly: with no passkey yet, `passkeys.start` returns registration options and `finishEnroll` stores the first passkey; otherwise it returns an assertion bound to the user (purpose `meetings:verifySession`) and `finishVerify` checks it is that user's. Both mark the session. On the web, `PasskeyGate` in the root route shows the step (or, for an older account, a sign-out prompt) instead of the page.
- Sessions: sign-in sessions live in the Convex Auth component. `users.sessions` lists the caller's, `users.signOutEverywhere` revokes them, and owners can sign a member out everywhere (`members.signOutEverywhere`). Revoking takes effect immediately because `getAuthUserId` checks the session.
- Rate limits: `lib/rateLimits.ts` (`@convex-dev/rate-limiter`) caps invites and link creation per org, and accepting invites, links or domain joins per user. Call `enforceRateLimit` in the mutation before the work.
- Slow mode: `meetings.slowModeSeconds` (0 to 600, chosen when scheduling, when opening a room, or later in the Access card) lets each person send one chat message per that many seconds. `enforceSlowMode` is a one-token bucket per meeting member with the period passed inline. Hosts and meeting managers are exempt.
- Public rooms (`models/rooms.ts`, `models/roomAccess.ts`): a public room is a meeting with `access: "public"` plus a `rooms` row. People with `manageMeetings` open one with `rooms.create` (an instant group call, so every meeting function works on it) and close it with `rooms.close`; it never ends just because it emptied. Anyone enters: signed-in people through the existing door (`meetings.enter`), guests through `guests.enter` with a device id, which gives them the `call_public_guest` preset (no mic, camera or screen share). `rooms.people` is recounted from `callPeers` whenever a peer joins or leaves (`syncRoomPeople`), and it lives on `rooms` so a join doesn't re-run every query that reads the meeting. A room holds 50 people (`ROOM_CAPACITY`). In a public room recording, drawing, snapshots, avatars and recap-ready notifications are off, `meetings.get` returns no emails and shows visitors only the hosts, and `meetings.mine` leaves the room out. `rooms.directory`, `rooms.preview`, `rooms.recaps` and `rooms.recap` are `publicQuery`s that return only the title, description, organization name, people count, slow mode, whether there is a waiting room and, for recaps, times and a checked summary. `roomAccess.ts` imports no other model.
- Waiting room (`rooms.waitingRoom`, set when opening a room or in its settings card): the room's own organization still walks in, and everyone else asks first. It reuses asking to join: a signed-in person asks from the door, a guest asks from `/rooms/<code>` and waits on their `/guest/<secret>` page, and hosts answer from `JoinRequests`. `hasWaitingRoom` in `roomAccess.ts` is what `canEnter`, `canAsk` and `guests.enter` check. A guest's request keeps their device id so the pass they get on admission carries it, and a banned person or device can't ask. Hosts of a public room get an inbox item for the first person waiting, not for each one after.
- Waiting room counts (`lib/aggregates.ts`): the Aggregate component (`@convex-dev/aggregate`, mounted as `waitingRoom`) keeps three counts per meeting, each a namespace `[meetingId, "waiting" | "joined" | "admitted"]` holding user ids. `models/joinRequests.ts` is the only writer: asking adds the person to `waiting` and `joined`, admitting moves them from `waiting` to `admitted`, denying takes them out of `waiting`, and cancelling the meeting clears all three. Inserts are `insertIfDoesNotExist`, so someone who is denied and asks again is counted once. `rooms.waitingRoom` returns the three numbers to hosts and meeting managers, and the room's settings card shows them. The counts cover `ask` meetings too.
- Moderation (`lib/moderation.ts`, `models/moderation.ts`, `internal/moderation.ts`): everything people put into a public room is judged by Jev 1.14 through the Convex AI Gateway (`lib/jev.ts` posts to `/alpha/decisions` with `getServiceToken("ai-gateway")`, so there is no API key; the gateway needs a paid Convex plan). Jev returns probabilities and `lib/moderation.ts` holds every question, threshold and rule, so that file is the one to audit: `decideMessage`, `decideName`, `decideFrame` and `penaltyFor` are plain functions with tests. Checks run as actions on `moderationWorkpool` with retries, queued by `models/moderationQueue.ts`, and each one's `onComplete` mutation applies the verdict. A chat message is inserted `pending` and only its author receives it until it passes; a removed message is deleted and its text kept on a `moderationFlags` row; a check that keeps failing drops the message and blames nobody. A removal is a strike, three strikes in 24 hours or one severe message is a ban (`bans`: 24 hours, then 30 days for a repeat, until lifted when a manager bans from a flag). Bans cover the org's public rooms and are checked on entering, joining the call, chatting, reacting and reporting frames; a guest's ban also carries their device id. Hosts and meeting managers are never struck or banned. Guest names are checked on entry and rename, and a rude one becomes "Guest". Call summaries are checked before `rooms.recap` shows them (`meetingSessions.summaryCheck`).
- Frame checks: RealtimeKit gives the backend no video, so each browser in a public room's call samples one other person's camera or screen share about every 45 seconds, at a random point between 22 and 67 so browsers don't line up (`call/frame-sampler.tsx`). It first asks `moderation.frameUploadUrl`, which returns no URL when that person was checked in the last 30 seconds, so frames that would be thrown away are never uploaded. Then it uploads a small JPEG and calls `moderation.submitFrame`, which accepts one frame per person per 30 seconds. Public rooms have no whiteboard or other plugins, since nothing drawn there would be checked. Jev asks four questions of each frame (nudity, a sexual act, gore, a hate symbol), and every one is a ban offence: a confirmed frame scoring 0.7 or more bans the person and kicks them from the call, with no strike step. A frame is confirmed when a host or meeting manager reported it, or when two different participants reported it within 5 minutes and at least one of them is signed in. A browser can upload any image, so this stops one person getting someone banned with a forged upload, and guests (whose identities are free) can't confirm each other. An unconfirmed flagged frame raises a `watch` flag, which `moderation.watch` hands to the other browsers so they sample that person at once. When nobody left in the call could confirm it, the frame goes to the managers' inbox instead (`moderationReview`), and the Moderation tab shows who reported it. Clean frames are deleted immediately and kept ones after 7 days (`dropEvidence`). Audio is not checked.
- Free usage limits (`models/usage.ts`, enforced every minute by `crons.ts` → `internal.usage.enforce`): Cloudflare usage is kept under the included amounts, with margin. `usage` rows are counters keyed by kind and UTC month or day. Call minutes count per device (`callPeers.connectedAt`) and stop at 9,000 a month: joins are refused and live calls are ended. Recording minutes (from `recording.statusUpdate`) stop at 90 a month: joins pass the minutes left as `recording_config.max_seconds`, and running recordings are stopped at the limit. Workers AI Neurons are estimated per UTC day: live text (Nova-3, per-device `callPeers.liveText`) switches off on every preset at 5,000, and calls that start after 7,000 skip the transcript and summary. Invite emails stop at 2,700 a month. Each person can create 10 meetings a day (`meeting` rate limit).
- Tests sit next to the code (`*.test.ts`). Convex never deploys files with two dots in the name. Tests use `convex-test` and run with `pnpm test`.

### Why `api.api`

Convex names functions after their file path, so `convex/api/users.ts` becomes `api.api.users`. Inside the backend that full path is used as is. Clients import the re-export instead:

```ts
import { api } from "@meetings/backend";

api.users.viewer;
```

`@meetings/backend` exports `api.api` as `api`, plus the `Doc` and `Id` types. It never exports `internal`.

## Web app (`apps/web/src`)

Layers depend downward only: `routes` → `layouts` → `features` → `components` / `lib`.

| Path                 | Contains                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `start.ts`           | Global request middleware (security headers, CSRF for server functions) and client-only rendering (`defaultSsr: false`)  |
| `providers/`         | App-wide providers (`ConvexWithAuthProvider` wires Convex and Convex Auth)                                               |
| `routes/`            | Route config, search-param validation, auth gates, and handing URL state to layouts and features                         |
| `layouts/`           | Page frames that compose features: `app-shell/` (sidebar and header for signed-in pages), `public-shell/` (public rooms) |
| `features/<domain>/` | UI plus Convex calls for one domain: `auth`, `meetings`, `orgs`, `rooms`, `schedules`                                    |
| `components/`        | Domain-free building blocks with no Convex calls: `EmptyState`, `FormError`, `LoadingScreen`                             |
| `lib/`               | Pure helpers, such as `emails.ts` (`splitEmails` for pasted email lists)                                                 |

Rules:

- `/` is the public landing page (`features/landing`). It renders on the server (`ssr: true`) so link previews, search engines and agents get the full page without JavaScript. Signed-in visitors are sent to `/home`, the signed-in home.
- The root route renders on the server for `/` and `/rooms…` and is `"data-only"` everywhere else. Other public routes (`/sign-in`, `/invite`, `/join`, `/guest`, `/m`) are `ssr: "data-only"`, so their `head` reaches the server HTML while their components render in the browser. Signed-in routes stay client-only.
- Public rooms pages (`/rooms`, `/rooms/<code>`, `/rooms/<code>/recaps/<n>`) are `ssr: true` inside `layouts/public-shell`. Each route's `loader` reads its first data with `convexHttp` (`providers/convex.tsx`), so the server HTML and the `head` carry every room's title and description; the component then switches to the live `useQuery`. They show times in UTC so the server and the browser render the same text. Signed-in people stay on these pages too: `/rooms/<code>` shows them the meeting page itself (the door, the call and the chat) inside the public shell, because the app's own pages need an organization and a visitor from the internet may not have one. Its sign-in links come back to `/rooms/<code>`, and a public room's meeting page links its recaps to the public recap pages. `/public-rooms` is the in-app page (`features/rooms`): Browse for everyone, Ours for the active org's rooms, and Moderation (flags and bans) for people with `manageMeetings`.
- Heads come from `lib/seo.ts`: `SITE_META` and `SITE_LINKS` on the root (Open Graph image, icons, `noindex` by default), and `pageHead` per public page. Pass `canonicalPath` only for pages search engines should index.
- `public/robots.txt` allows every crawler. `public/llms.txt` tells agents which pages exist and which URL parameters set their state, so update it with any route or `validateSearch` change. `public/sitemap.xml` lists the indexable pages.
- `apps/web/src/server.ts` is the Worker entry (`main` in `wrangler.jsonc`). AI crawlers don't run the Databuddy script, so it reports every request to Databuddy with `trackAgents` in `waitUntil`; the SDK sends only AI agents and skips assets. `.txt` and `.md` paths run the Worker first (`assets.run_worker_first`) so `llms.txt` and `robots.txt` reads are counted, then come from `env.ASSETS`. The Databuddy ID is public and lives in `lib/databuddy.ts`.
- The logo is `components/logo.tsx`. `public/favicon.svg`, `public/apple-touch-icon.png` and `public/og.png` are drawn from the same strokes.
- Settings live behind the user menu at the bottom of the sidebar: `/settings/account`, `/settings/general` (appearance, time zone and hours), `/settings/meetings` and `/settings/org`. Per-person preferences are the `userSettings` table (`api.settings.getMine` / `setMine`, defaults in `models/settings.ts`).
- Theme: `lib/theme.ts` puts `dark` or `light` on `<html>` (Kloq and COSS both follow it), remembers the choice locally, and an inline `THEME_SCRIPT` restores it before paint. The saved `userSettings.theme` is applied on a new device. Calls pick RealtimeKit's light or dark tokens from it.
- UI state lives in the URL. Routes declare it with `validateSearch`. Examples: `/schedule?zone=…&zones=…&view=list`, `/calendar?zones=…&new=true&start=…`, `/sign-in?redirect=…`.
- Changing URL state:
  - Declarative navigation is a `<Link>` anywhere: features, layouts or routes.
  - Imperative navigation (`navigate`) belongs to routes. Features receive it as callbacks (`onClose`, `onInvite`).
- Server data comes from Convex `useQuery` / `useMutation`.
- Times are UTC milliseconds plus an IANA zone name, converted with Luxon in `lib/schedule.ts`. No hand-written UTC offsets. Its tests sit next to it (`schedule.test.ts`) and run with `pnpm test`.
- URLs carry no table ids. Meetings are `/meetings/<code>`, and a recap is `/meetings/<code>/recaps/<n>`, the nth call of that meeting (`meetingSessions.number`). Secret links (`/invite`, `/join`, `/guest`) are the only long tokens.
- The active organization is a saved preference (`userSettings.activeOrgId`), not part of the URL. `orgs.setActive` switches it (optimistically, through `useSwitchOrg`); creating or joining an org makes it active. `OrgGate` falls back to the first org, or asks to create one. Features read it with `useActiveOrg()`.
- Org names: nobody can be in two orgs with the same name (case-insensitive), so the switcher never shows duplicates. Names don't need to be unique across everyone.
- Scheduling starts with only the organizer; people are added from the org with `PeoplePicker`.
- The calendar passes Kloq controlled, read-only events keyed by meeting code, with the meeting link, your reply as an attendee and, for the selected event (`/calendar?event=<code>`), everyone's replies from `meetings.get`. Kloq's own panel shows them. Unanswered invites are drawn as free (hatched). Declined meetings are hidden unless `?declined=true`. Clicking or dragging an empty slot, or Schedule meeting in its toolbar, opens the schedule form in a dialog over the calendar (`?new=true&start=…&minutes=…`); scheduling closes it and selects the new meeting.
- Find a time shows the org's members (`features/orgs/people.ts` maps them to `Person`). Busy times come from `meetings.busy`, and the calendar and Home read `meetings.mine`.
- Home (`/home`) is the launchpad: Start now, Join with a code and Schedule (`features/meetings/launchpad.tsx`), then Live now, Needs your reply with Going and Not going, Coming up by day, and Recent recaps (`upcoming-meetings.tsx`). Live now lists your meetings whose open session has people in it (`meetings.mine` returns `lastSession.inCall`, the number of members connected), so it works without `manageOrganization`. Coming up shows Join from 10 minutes before the start. Every Join and every pasted code opens `/meetings/<code>?call=true`, which goes straight to the lobby. The header hides Start, Schedule and the code box on Home because the launchpad has them.
- The meeting page (`features/meetings/meeting-page.tsx`, also used for public rooms) has one header with the title, a status badge (LIVE, a countdown from 10 minutes before the start, or Ended), the link and a single Join button. Invitees reply with Going or Not going there; hosts get a ⋯ menu with Cancel meeting, or Close room and Delete room. Below are tabs in `?tab=` (`chat`, `recaps`, none for Overview). Overview holds People (`meeting-people.tsx`, where host controls sit in each person's ⋯ menu), the Access card and the last call's recap.
- Who is in a call: `meetings.get` marks each person `inCall` from the meeting's `callPeers`. People shows "In the call" beside them, and the lobby says who is already in (`nameList` in `lib/names.ts`). The lobby folds the microphone, camera and speaker pickers into one Devices row and says whether you'll go in with your mic and camera on.
- In the call, the controls sit in one floating dock over the bottom of the stage (`call/call-room.tsx`): Ask to speak when it applies, mic, camera, share, Chat, People, More and Leave. More holds picture-in-picture, recording, polls, whiteboard and plugins, AI transcript, breakout rooms, settings and full screen. The header shows a running call timer (`useSecond` and `formatElapsed`).
- After you leave, or a host ends the call, the left-the-call screen (`call/call-ended.tsx`) keeps Back to meeting and Rejoin. When the meeting has recaps on, it adds a note that the summary and transcript show up on the Recaps tab, and in the Inbox for signed-in people, a few minutes after the call ends.
- Search-param updates that only change what is shown pass `resetScroll: false`, so the page doesn't jump to the top.
- Form state comes from TanStack Form (`useForm`). Server errors come back through `validators.onSubmitAsync`.
- No `useEffect`. Scroll, layout and visibility use CSS or declarative components (`<Authenticated>`, `<Navigate>`). For example, the invite chat stays scrolled to the newest message because its scroll container is `flex-col-reverse`. A browser API that needs setup and teardown goes in a ref callback that returns its cleanup (React 19), on an element that mounts and unmounts with it, as `AgentTools` does. A value that changes with time uses `useSyncExternalStore`, as `useMinute` (`features/meetings/clock.ts`) does for Home's countdowns.
- Agent tools: `AgentTools` (`features/meetings/agent-tools.tsx`) sits in the `_app` layout, so it exists only while signed in, past the passkey step and inside an org. In a browser with WebMCP (`document.modelContext`; Chrome's origin trial or `chrome://flags/#enable-webmcp-testing`) it registers typed tools with `registerTool`: list upcoming meetings, schedule a meeting, start one now, open a call by code, and reply to an invite. A ref callback on a hidden `<span>` registers them all with one `AbortController` and returns `controller.abort` as its cleanup, which unregisters them. Each tool calls the same Convex function the UI calls, so the server checks auth and permissions, and navigation goes through the route's callback. Meetings are named by code and people by email, never by table id. Tools return `{ error }` instead of throwing, because WebMCP drops a rejection's message. Each call is tracked as `agent_tool_called` with the tool name and `navigator.userAgent`: WebMCP tells a tool nothing about the agent calling it, so the browser's user agent is how Databuddy tells agents apart. Databuddy's `trackMcp` doesn't apply, because it wraps a server-side MCP SDK server and needs a secret API key. `public/llms.txt` lists the tools for agents.
- Allowed `useState`, until the data lives in Convex:
  - `features/meetings/invite-panel.tsx`: the local chat messages and composer draft.
  - COSS components' own internal state in `packages/ui`.

## AI participants (design, not built)

How a bot such as Claude or Grok would join a call:

- **Seat in the call:** a RealtimeKit agent participant. Add a participant with a dedicated `agent` preset, then open `wss://api.realtime.cloudflare.com/agent-ws/v1?subscriptions=transcript,participant,chat` with its token and the `realtimekit.v1` subprotocol. It receives final transcript lines, joins and leaves, and chat. It can send chat, polls and broadcasts. This channel carries no audio.
- **Where it runs:** the WebSocket needs a long-lived holder, so it lives in a Durable Object, one per meeting, in a small `apps/agent` Worker. The Durable Object stores the resume `connection_id`, sends `connection.ping` every 20 s and closes with code 1000 when the meeting ends. An open agent keeps the session, and its billing, alive.
- **Brain in Convex:** the Durable Object posts final transcript lines to a Convex HTTP action signed with a shared secret. Convex stores them per session. When someone writes "@Claude" in our chat, a Convex action calls Claude through `@anthropic-ai/sdk` with model `claude-opus-5-5`, adaptive thinking and streaming. The system prompt and the transcript so far are a cached prefix (`cache_control`), and the question comes after it. The answer is posted to our Convex chat as the bot. Tools: summarize so far, list action items, start a poll (sent back to the Durable Object as a request), schedule a follow-up (an existing Convex mutation). Needs `ANTHROPIC_API_KEY`.
- **Voice:** Claude has no audio input or output. A speaking Claude needs speech-to-text → Claude → text-to-speech plus a media track in the call (Cloudflare Realtime Agents pipeline, e.g. Workers AI or Deepgram and ElevenLabs). Grok has a speech-to-speech realtime API (`wss://api.x.ai/v1/realtime`, `grok-voice-latest`, `XAI_API_KEY`), but its audio still needs the same media bridge into the call.
